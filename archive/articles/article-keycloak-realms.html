One identity provider, two realms, two origins

Two apps, each with its own realm and its own public hostname, served by one identity provider. The hard part is not the signature, it is the issuer.

the issuer is the hard part

Two applications each ran their own Keycloak. That looked necessary, because each realm's issuer has to equal the origin the browser actually used, and the two apps are reached on different hostnames. Keycloak builds the issuer from the origin it believes it is served on: https://<host>/realms/<realm>. A resource server does not merely verify the signature — it checks that the token's iss claim equals its configured issuer character for character.

The naive knob, KC_HOSTNAME, is global: one value for the whole server. Set it to one app's hostname and the other app's redirects point at the wrong place. Leave it unset under start-dev and Keycloak advertises localhost, which no remote browser can reach.

The mechanism that makes it work is a per-realm attribute that outranks the global hostname. Keycloak resolves the origin it advertises in this order: 

1st  realm frontendUrl
2nd  global KC_HOSTNAME
3rd  request Host header

Verify it, don't trust it. The decisive test asks with no Host header at all, so nothing request-derived can be involved — only realm data can produce the answer. Two different public origins from two discovery documents on one port is proof. Discovery documents prove advertising though, not login, so the end-to-end check was a real authorization-code flow: PKCE verifier, POST the credentials, read ?code= out of the 302, exchange it, decode the access token, and then call the API with it. A 401 there means the issuer did not match; a 200 means the resource server validated a token minted by the shared instance.

838 MB saved — 631 MB for one instance against 784 MB + 685 MB for two. That is the largest single memory win after the JVM retune, and unlike most of the others it is justified on memory alone.

The second half of the problem is redirect URIs, which rotate with the tunnel hostname. Updating the issuer but not the client's registered redirect URIs fails in the browser with HTTP 400 Invalid parameter: redirect_uri — while every curl check still passes, because curl never follows the browser's path. Both are now written together, per realm, from one script.

The importer is filename-sensitive: a realm named workflow-realm must live in workflow-realm-realm.json. And a realm export is not a deployment manifest — exports capture what was configured when they were written, so the deploy origin has to be applied at deploy time.
