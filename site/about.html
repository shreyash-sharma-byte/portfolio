About

How I work

Architecture before code, measurements rather than estimates, and a habit of writing down the result — including when it contradicted the estimate I started with.

I am a full-stack engineer with three years of professional experience, working mainly on insurance and banking platforms. In practice that means Java and Spring Boot services, Angular front ends, and relational databases: PostgreSQL by preference, and Oracle with PL/SQL where the data already lives. I also know the business side, not just the build: how insurance and banking processes actually run.

I work architecture first. Before writing code I want to know what the request path is, who is allowed to call it, what happens when it fails halfway through, and how I will know it worked. That habit is why the engineering articles are mostly about things that broke and what the measurement said afterwards — two of those results contradicted the estimate I started with, and the measured number is the more useful one to publish.

I am comfortable being the person who talks to the business side as well as the code: gathering the requirement properly, saying early when something will not work, and writing the decision down so the next engineer does not have to rediscover it. I am open to full-time full-stack, Forward Deployed Engineer, and AI Engineer roles.

What I bring

Backend and platform

  • Service boundaries that hold. Eight Spring Boot services with a shared config server and service discovery, each owning its own database — five databases, no shared tables, cross-service references enforced in application code rather than by a foreign key that spans them.
  • Concurrency taken seriously. Money transfer as a single ACID transaction with a conditional update, so two concurrent requests cannot overdraw an account; optimistic locking by version compare-and-swap so a stale write gets a conflict instead of silently overwriting.
  • Delivery that survives failure. A transactional outbox moves ledger entries through PENDING → SENDING → PUBLISHED with batch confirmation, retry and error states — so an event is never lost because a broker was briefly unavailable, and never applied twice.
  • Schemas that age. Thirty Flyway migrations on the insurance platform; monthly partition windows with a DEFAULT catch-all on the banking ledger, after a single hardcoded partition expired and started rejecting every insert.

Identity, authority and audit

  • Federated sign-in across two realms. OIDC with PKCE against Keycloak, with per-realm origin advertising so a single Keycloak instance can serve two realms on two different public hostnames — verified end to end with a real authorization-code flow, not just a discovery document.
  • Authority modelled, not improvised. Per-product approval limits where a decision above the actor's level becomes a proposal referred upward, and a maker-checker path on configuration changes.
  • Permissions attached to the work. Nine realm roles enforced at the station an instance currently sits at, rather than globally — so the same user can approve at one step and not at the next.
  • Audit that cannot be edited. Append-only history with no update or delete endpoint, and in the insurance platform a database trigger that rejects both at the data layer.

Front ends and applied AI

  • Angular in production shape. Angular 17 and 22 with typed service layers that mirror the API contract, route guards, HTTP interceptors and signals for async state.
  • Hand-written design systems. Plain CSS with semantic tokens, no framework and no icon library, verified at 390px and 1280px with no horizontal scroll.
  • Retrieval over recall. Clause retrieval from a FAISS index with cross-encoder re-ranking, answers that cite the sources they used, and an explicit refusal path when retrieval confidence is too low to answer.
  • Evaluation as a first-class step. A local harness scoring section match, top-1 accuracy, mean reciprocal rank and coverage polarity — run against a fixed question set, and costing nothing because it never calls a model.
