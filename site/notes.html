Engineering notes

Measured, not guessed

Seven things that broke, and what the numbers said when I actually measured them. Two of these contradicted the estimate I started with — the honest result is the more useful one, so it is the one written down here. Everything below was observed on the machine that serves these projects.

Layout · flexbox

A 784px column inside a 390px viewport

The signed-in shell is a sidebar and a main column in a flex row. On a phone it scrolled sideways. The cause was one missing declaration: the main column was flex: 1 without min-width: 0. A flex item's default min-width is auto, which means it cannot shrink below its content's intrinsic width — so wide children (a nowrap table, a filter bar) sized the column itself, and every descendant inherited the overflow.

Measured, the main column computed 784px wide inside a 390px viewport.

The instructive part is the first fix attempt. Per-component media queries were added to the widest children; it compiled cleanly, every string check passed, and nothing changed — because the column was sized by its content, not by the components inside it. The fix had to be structural: constrain the flex item, then let children shrink. Verified numerically rather than visually — scrollWidth went from 784 to 390 on four routes, with zero elements extending past the viewport.

JVM · memory

JVM tuning that was measured, not guessed

Nine Spring services and a Kafka broker were running with -Xms256m -Xmx1g, inherited from a container template. Observed live sets were 94–170 MB, so the 1 GB ceiling bought nothing — but it did make the collector lazy, which is how a Java service's RSS climbs quietly over hours.

What replaced it, per service: 

-Xms128m -Xmx384m -XX:MaxMetaspaceSize=256m
-XX:ReservedCodeCacheSize=96m -XX:+UseSerialGC

Kafka got the same treatment through its own environment variable, because the image default is -Xms1G -Xmx1G — a gigabyte committed for a broker holding a handful of demo messages. It now runs -Xms256m -Xmx512m.

Results. Committed heap per service fell from 256 MB to about 123 MB. Across the ten retuned JVMs, RSS went from 5,181 MB to 3,719 MB — roughly 1.4 GB. Whole-machine JVM footprint went from 7,344 MB to about 5,890 MB across 15–16 JVMs.

The caveat, stated plainly. The "before" column was measured on services warmed up for 20–40 minutes; the "after" column about 10 minutes after a restart. Some of that delta is therefore warm-versus-cold, not flags. The part that is attributable to the flags is mechanistic and solid — committed heap dropping from 256 MB to ~123 MB is -Xms alone, plus SerialGC's saved threads and collector structures.

What was deliberately left alone matters as much: -Xss512k (thread stacks are reserved, not resident — the real saving is a few MB against a real StackOverflowError risk), -XX:MaxDirectMemorySize (the gateway is Reactor Netty and does its I/O through direct buffers), -XX:TieredStopAtLevel=1 (right for batch jobs, 2–5× slower at peak throughput), and ZGC/G1 (both cost more than SerialGC at this heap size).

Three traps in reading these numbers: committed is not resident (ZooKeeper runs a 512 MB committed heap at ~117 MB RSS); warm is not cold; and snapshot totals move on their own, because a container healthcheck that shells out to kafka-broker-api-versions starts a fresh JVM on every run.

Infrastructure · the result that contradicted the estimate

The consolidation that saved 38 MB, not 150

Seven per-project Postgres containers were merged into one shared instance. The estimate was 100–150 MB. The measurement was ~38 MB.

The estimate was wrong for a good reason: Postgres's per-instance overhead is small, and connection backends dominate the footprint. Seven idle servers do not cost seven times one server.

The consolidation was kept anyway, on operational grounds rather than memory: one backup target, one connection point, and the next project needs no new database server at all. Publishing the honest number next to the decision is a better signal than a fabricated win.

Two related decisions came out of the same exercise. First, separate databases rather than separate schemas inside the shared server — the database name is what every application already specifies, so connection strings change only in host and port; isolation is enforced by Postgres rather than by convention; and it avoids the shared public schema, extension collisions and migration tools that assume they own the database.

Second, and more importantly, what was not consolidated. Collapsing all the Spring services into one JVM was superficially attractive — several Spring Boot apps can share a runtime, each with its own port and datasource, and the module structure survives. What does not survive is independent deployability: no independent restart, no fault isolation, one heap for every service, one classpath for every dependency, and process-global state fighting you through system properties, static initialisers and shutdown hooks. That produces a modular monolith — respectable, but a different architecture, and it would have made the repository's own description false. Estimated saving: ~2.1 GB, permanently trading the thing the project exists to demonstrate. Rejected.

Identity · the issuer is the hard part

One identity provider, two realms, two origins

Two applications each ran their own Keycloak. That looked necessary, because each realm's issuer has to equal the origin the browser actually used, and the two apps are reached on different hostnames. Keycloak builds the issuer from the origin it believes it is served on: https://<host>/realms/<realm>. A resource server does not merely verify the signature — it checks that the token's iss claim equals its configured issuer character for character.

The naive knob, KC_HOSTNAME, is global: one value for the whole server. Set it to one app's hostname and the other app's redirects point at the wrong place. Leave it unset under start-dev and Keycloak advertises localhost, which no remote browser can reach.

The mechanism that makes it work is a per-realm attribute that outranks the global hostname. Keycloak resolves the origin it advertises in this order: 

1st  realm frontendUrl
2nd  global KC_HOSTNAME
3rd  request Host header

Verify it, don't trust it. The decisive test asks with no Host header at all, so nothing request-derived can be involved — only realm data can produce the answer. Two different public origins from two discovery documents on one port is proof. Discovery documents prove advertising though, not login, so the end-to-end check was a real authorization-code flow: PKCE verifier, POST the credentials, read ?code= out of the 302, exchange it, decode the access token, and then call the API with it. A 401 there means the issuer did not match; a 200 means the resource server validated a token minted by the shared instance.

838 MB saved — 631 MB for one instance against 784 MB + 685 MB for two. That is the largest single memory win after the JVM retune, and unlike most of the others it is justified on memory alone.

The second half of the problem is redirect URIs, which rotate with the tunnel hostname. Updating the issuer but not the client's registered redirect URIs fails in the browser with HTTP 400 Invalid parameter: redirect_uri — while every curl check still passes, because curl never follows the browser's path. Both are now written together, per realm, from one script.

The importer is filename-sensitive: a realm named workflow-realm must live in workflow-realm-realm.json. And a realm export is not a deployment manifest — exports capture what was configured when they were written, so the deploy origin has to be applied at deploy time.

Database · a time bomb with a date on it

The partition that expired on the first of the month

Two tables were range-partitioned by timestamp with exactly one hardcoded partition each — the month the project was written. While the calendar sat inside that month, everything worked. Once it moved past it, every insert had nowhere to go and failed.

The failure mode is what made it interesting. It surfaced as a 500 on account creation and on every transfer — because the audit row is written in the same transaction as the transfer. A partitioning detail in one table took down an unrelated user-facing flow.

Fixed with a rolling window of monthly partitions plus a DEFAULT catch-all on each table, so an unroutable row is now impossible rather than merely unlikely. Concrete months are still created ahead of time by a script on a monthly timer, because they are what makes old partitions cheap to prune.

Networking · an allow-list that could never match

A CORS rule that could never work

The API gateway's CORS allow-list named only localhost:4200 and localhost:4201. The demo is reached through a tunnel whose hostname changes on every restart, so no fixed list could ever contain it.

The confusing part is the asymmetry it produced. Browsers send an Origin header even on same-origin POSTs, so logins failed with 403 in the browser — while the same request from curl, which sends no Origin at all, succeeded. One request, two verdicts, depending only on who sent it.

The durable fix is a pattern-based allow-list with an environment override (allowedOriginPatterns), so any localhost port works out of the box and a deployment sets its own origin. The verification matters more than the change: an allowed origin gets 200 and an unlisted one still gets 403 — the policy was made workable, not made permissive.

Process · keeping the public repos honest

Deploying without touching the source repositories

Serving a project usually means editing it — a build path, an origin, a config flag — and those edits end up in the public repository as noise, or worse, as a deployment concern that leaks into a codebase someone else is reading.

Here the deployment wiring lives in separate clones, kept as re-appliable patches, and the originals stay byte-identical to their last commit — git status in them reports nothing. The build scripts read only from the clones. So a rebuild cannot re-introduce wiring into a project repository, and a change in a project repository cannot silently un-patch what is being served.

The wiring itself is deliberately the smallest change that makes a frontend deployable: read the API origin at runtime from a global the edge injects, instead of compiling a default in. Everything else — units, containers, proxying — lives outside the projects entirely.

Smaller traps worth writing down

  • A single-file bind-mount serves a stale inode. Editing a config on the host and reloading inside the container changed nothing — the mount still pointed at the old file, and nginx -t happily validated it, which is the tell that you are testing the wrong thing. Mount the directory, or recreate the container.
  • docker compose up resurrects what you retired. Both depends_on and a start script with no service arguments will pull a removed dependency back up. Retired services now sit behind a non-default profile, invisible to a plain up -d.
  • A container restart does not re-read env_file. Only a recreate picks up changes. This bit twice, through a Django ALLOWED_HOSTS setting.
  • Angular's emulated encapsulation does not protect a component from global selectors. A landing page reused class="steps"; the app's global stylesheet already had .steps li { display: flex } for its own stepper, and every text run in the list became a separate flex item. It compiled cleanly and every string check passed. Namespace the classes you introduce.
  • Write the string before you open the file. open(path, "w").write(<expression that raises>) truncates the file the instant open() is called, because the argument is evaluated afterwards. A formatting error silently emptied an 8,828-byte stylesheet.
