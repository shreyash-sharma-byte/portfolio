JVM tuning that was measured, not guessed

Nine Spring services and a broker, retuned twice from measurement. Two attempts failed, and the correction to my own thread-stack claim is the part worth keeping.

JVM · containers

Nine Spring services and a Kafka broker were running with -Xms256m -Xmx1g, inherited from a container template. Observed live sets were 94–170 MB, so the 1 GB ceiling bought nothing — but it did make the collector lazy, which is how a Java service's RSS climbs quietly over hours.

The heap was also the wrong place to look first. On the busiest of the nine, RSS was 472 MB: about 126 MB of committed heap, of which only ~63 MB was live, against 107 MB of metaspace, ~50 MB of JIT code cache and ~6 MB of thread stacks. Tuning -Xmx tunes less than a third of the process.

Two rounds of measurement followed. The first replaced the inherited flags per service: 

-Xms128m -Xmx384m -XX:MaxMetaspaceSize=256m
-XX:ReservedCodeCacheSize=96m -XX:+UseSerialGC

Kafka got the same treatment through its own environment variable, because the image default is -Xms1G -Xmx1G — a gigabyte committed for a broker holding a handful of demo messages. It moved to -Xms256m -Xmx512m.

Round one results. Committed heap per service fell from 256 MB to about 123 MB. Across the ten retuned JVMs, RSS went from 5,181 MB to 3,719 MB — roughly 1.4 GB. Whole-machine JVM footprint went from 7,344 MB to about 5,890 MB across 15–16 JVMs.

The caveat, stated plainly. The "before" column was measured on services warmed up for 20–40 minutes; the "after" column about 10 minutes after a restart. Some of that delta is therefore warm-versus-cold, not flags. The part that is attributable to the flags is mechanistic and solid: committed heap dropping from 256 MB to ~123 MB is -Xms alone, plus SerialGC's saved threads and collector structures.

The second round halved the committed heap on the nine services again and applied the same discipline to the remaining containers: 

-Xms64m -Xmx256m -XX:MaxMetaspaceSize=192m
-XX:ReservedCodeCacheSize=64m -XX:+UseSerialGC
-XX:TieredStopAtLevel=1
-XX:ActiveProcessorCount=2
-Xss512k

That took the heap ceiling from 384 MB to 256 MB and the committed floor from 128 MB to 64 MB. Keycloak went from 700 MB to 380 MB, Zipkin from 283 MB to 143 MB, Kafka from 462 MB to 405 MB and ZooKeeper from 122 MB to 77 MB. Five unused tunnels left over from the previous hostname scheme were still running, 128 MB across five processes serving URLs nothing linked to; they were stopped after confirming that no live identity-provider origin pointed at them. The whole demo stack went from 5,512 MB to 3,404 MB, down 2,108 MB or 38%.

Attribution, again. Of the 1,351 MB saved across the nine services, roughly 576 MB (9 × 64 MB) is mechanically certain: it is the -Xms halving, and it would hold even if the "before" snapshot were re-measured warm. The rest is a mix of smaller code cache, fewer JIT and GC threads, and metaspace and GC-structure differences, measured in place.

The reason Keycloak was the outlier for so long is worth keeping. Its image sets -XX:MaxRAMPercentage=70, and the container it ran in declared no memory limit, so the JVM sized its maximum heap against the host's full 31.8 GB and felt free to grow. An explicit -Xmx appended last on the command line wins over the percentage. A percentage is the right tool when a container limit exists; an explicit ceiling is clearer when it does not.

Failure one: the collector was already chosen. I added -XX:+UseSerialGC to Keycloak's appended options, reasoning that a small heap wants a serial collector. The image already selects one in its own options. Two selections is not a last-one-wins situation, it is a hard startup error: 

Error occurred during initialization of VM
Multiple garbage collectors selected

With Restart=always on the unit, the container entered a restart loop and Keycloak was down, which took logins for two demos with it. It was caught because the readiness poll run immediately after the recreate never returned 200, so I read the container log and saw the error. Removing the flag and recreating brought it back in 25 seconds. Appending flags to a vendor image is not neutral: you are arguing with defaults you did not write, so read them first. The other half of the lesson is that a single-instance critical service should never be recreated without a readiness check in the same command. The poll is what turned a silent broken state into a two-minute fix.

Failure two: class-data sharing crashed the JVM. Nine Spring services each commit 44–107 MB of metaspace loading largely the same framework classes, so archiving those classes once and memory-mapping them looked like the remaining structural win. The archive built cleanly at 100 MB. Starting a JVM with it segfaulted inside HotSpot while reading the shared archive, and with Restart=always it crash-looped for four minutes and wrote 25 crash dumps before it was stopped. Deleting the archive and the override had the service serving again 15 seconds later. -Xshare:auto, the default, is supposed to ignore a bad archive; a corrupt or incompatible one can still crash the VM. A CDS archive is also bound to the exact JDK build, classpath and flag set, so rebuilding a service invalidates it. The approach is abandoned here, and the earlier note calling it the next multi-JVM win now reads as attempted, crashed, do not retry.

The correction to my own earlier claim. An earlier write-up argued to leave -Xss512k and -XX:TieredStopAtLevel=1 alone, for two good reasons: thread stacks are cheap in practice, and C1-only JIT costs peak throughput. I set both anyway, and the measurement proved the first half of that right while making the size concrete. Forty-six thread stacks reserved 22.3 MB of address space but only 5.96 MB was resident, about 130 KB per thread. The "1 MB stack" is a reservation, not RAM. So -Xss512k is low value: a few MB per JVM, and it should not be sold as a memory win. -XX:TieredStopAtLevel=1 is a real trade rather than a free saving: it trims the code cache and removes the C2 compiler threads, but it does reduce peak throughput, and it is the first flag to remove if a demo ever feels sluggish.

What was deliberately left alone matters as much: ZGC and G1 (both cost more than SerialGC at this heap size), -XX:MaxDirectMemorySize (the gateway is Reactor Netty and does its I/O through direct buffers), and virtual threads. Java 21 virtual threads are for scaling concurrency, not for shrinking an idle process: with 30–47 threads per service the whole stack footprint is single-digit MB. Enabling them is a feature to demonstrate, not a memory optimisation.

Three traps in reading these numbers: committed is not resident (ZooKeeper runs a 512 MB committed heap at ~117 MB RSS); warm is not cold; and snapshot totals move on their own, because a container healthcheck that shells out to a Java command starts a fresh, short-lived JVM on every run.
