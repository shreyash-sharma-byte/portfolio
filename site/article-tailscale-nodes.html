Five public demos from one laptop

Five unrelated apps, five stable public hostnames, one machine. One node per app cost five identities and beat path prefixes for three concrete reasons.

one hostname per app, one node per app

Five demos, five different stacks, one machine. Each one needed a URL that does not change, because the URLs are published on the project pages and two of the apps run an identity provider whose issuer is pinned to the origin the browser used. A URL that rotates on restart is not a URL you can publish.

There were two shapes available. Put one hostname in front of everything and give each app a path prefix. Or give each app its own hostname and let it own the root, /, of that name. I chose the second. Each app gets its own node identity with its own *.ts.net hostname; that node terminates TLS and proxies to a port on the machine. Five apps means five nodes, which sounds expensive until you see why the alternative fails. 

ONE HOSTNAME, PATH PREFIXES
  host/claims      ->  app A
  host/workflow    ->  app B
  one origin, so /api is ambiguous

ONE NODE PER APP
  claims.host      ->  app A owns /
  workflow.host    ->  app B owns /
  one origin each, no prefix to rewrite

The three reasons path prefixes fail here. First, one of the front ends is built with a baked <base href="/">. Every asset URL is resolved from the root, so serving it under a prefix means rewriting the base at build time. That is a per-deploy edit to a repository whose whole point is that it stays untouched, and it has to be re-applied on every rebuild.

Second, root-relative API calls become ambiguous on a shared origin. The front end calls /api/...; with one hostname and five apps, the proxy has to decide which app's /api/ that is. One app can keep the path and the other four need their API calls rewritten to something prefixed, which is again a build-time change in each repository.

Third, one of the demos is a generated site whose own directories already occupy the paths a prefix scheme would want. A prefix is not free real estate: it collides with a directory the site already publishes, and the collision shows up as a 404 on a page that exists.

Per-app hostnames remove all three. Each app's root is its own, so the baked base is correct; each origin has exactly one /api/; and no generated directory has to be moved out of the way. The origin is also stable, so the identity-provider issuers and redirect URIs are configured once instead of being rewritten whenever a URL changes. The five nodes are independent processes with their own identities and their own certificates, which is what lets each one hold a hostname of its own.

What the platform constrains. Two limits shaped the design. A Funnel terminates TLS on one hostname per node, and only three ports are eligible: 443, 8443 and 10000. One hostname per node is the reason this is five nodes and not one node with five names; the port list is the reason every demo is HTTPS on 443. A third trap is worth knowing before designing around it: the private publish and the public publish use the same port numbers, and one port cannot be both at once. Whichever command touched the port last wins, so a demo that works for you and 404s for a stranger is a configuration-ordering problem, not a DNS problem.

The failure worth keeping. A Funnel created immediately after a new node comes online can fail to get its public DNS record at all. The local app answers the whole time; the name simply does not resolve for anyone outside. Public DNS records for a new Funnel can take up to ten minutes to appear, and in practice the useful wait is about five minutes before re-checking. The mistake was treating the first attempt as permanent. The fix that worked was deterministic: remove the Funnel and add it again, then wait and verify. Retrying the same command on the assumption that the app was broken would not have fixed it, because the app was never the problem.

Verification, because a local check lies. The same hostname resolves differently depending on who asks: from the machine it resolves through the private network straight to the node, and from the public internet it resolves to the relay that fronts it. A curl run on the box therefore exercises the private path, not the path a stranger's browser takes. The check that counts is the one made from outside the network. The control matters as much as the check: a nonsense hostname asked of the same relay must fail, or a 200 proves only that something answered.

The honest limit: all five demos and both realms run on one machine, so the machine is the availability boundary. If it is off, all five hostnames stop answering at once. The network layer is not the part that breaks.
