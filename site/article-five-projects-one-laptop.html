Five projects on one laptop

Five projects, one machine, and a platform layer that sits there at 1.8 GB whether anyone is looking or not. What is shared, what is deliberately kept apart, and what a sixth project would cost.

share the platform, never the services

Running five projects on one machine is not a memory problem. It is a duplication problem. Each project arrived with its own copy of everything a project needs: a database, an identity provider, a message broker, an edge proxy, a public ingress point. Every one of those is small on its own, and none of them is what the project is actually about. The copy is what grows.

Laid out that way, these five projects measured 13 GB. Ten of them would not fit in the machine at all. Nothing in that table is exotic; it is just what five independent stacks cost when each one insists on being complete.

So the machine is drawn in two layers, and the split is the whole design: 

ALWAYS ON  shared, one copy, ~1.8 GB idle
  postgres   one server, a database per project
  keycloak   one instance, a realm per project
  kafka      one broker, namespaced topics
  edge       one proxy, a block per project
  ingress    one node per app
  zipkin     tracing

ON DEMAND  only while a project is being shown
  the project's own services, and nothing else
  banking    8 services  ~1.9 GB

The first layer is idle by design — resident, serving nobody, most of the day. It is worth measuring rather than estimating, so here it is with no project open at all:

1.8 GB, flat. That number is the one that matters, because it is the one that is always there and it is the one a sixth project barely touches — the next project adds a database to an existing server, a realm to an existing provider, a block to an existing proxy and one more ingress node. Call it 80 MB, against 700 MB to 1.4 GB for a duplicated copy of the same thing.

The largest single line is the honest surprise, and it is not the database or the identity provider. It is ingress, at 432 MB across six node processes — 333 MB of that for the five per-app nodes alone. Stable public hostnames are paid for in memory, and at this scale that is a deliberate trade rather than a free one. It is argued in its own write-up.

That gives the rule the rest of this is built on: consolidate the platform, never the services.

The line, drawn once
Shared — one copy for every projectKept separate — one per project

One ingress node per appIts own release cycle

Databases, not schemas. Inside the shared server, each project gets its own database rather than a schema inside a common one. The database name is what every application already specifies, so a connection string changes only in host and port — no search-path wiring, no per-schema grants to remember. Isolation is then enforced by Postgres itself, separate catalogs and separate roles, instead of by convention. It also sidesteps the schema footguns: a shared public schema, extension collisions, and migration tools that assume they own the database they are pointed at. An identity provider, in particular, expects to own its database. Memory is identical either way; what costs is the container count, not the number of databases.

Why the services stay apart. The tempting second move is to collapse every service into a single JVM — several Spring applications can share one runtime, each with its own port and datasource, and the module structure survives. I priced it rather than guessed at it: about 2.1 GB. What does not survive the merge is independent deployability, which is the property the architecture is named for. One process means no independent restart, no fault isolation, one heap for every service, one classpath for every dependency version, and process-global state fighting the whole idea through system properties, static initialisers and shutdown hooks. The result is a modular monolith — a respectable shape, a different one, and it would make the projects' own descriptions false. Rejected at that price. The same ~1.9 GB comes back for nothing by starting a project when it is being shown and stopping it afterwards.

Two caveats. The idle numbers here are resident memory, not ceilings — a shared broker or identity provider grows under load, which is why the identity provider runs with an explicit heap ceiling instead of a percentage of the host; see the JVM write-up for what that cost when it was wrong. And shared is not coupled: no service in one project talks to a service in another. They share a server, an auth instance and an ingress point, and nothing else.
